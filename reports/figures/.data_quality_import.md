# Data Quality Report: Cookie Cats A/B Test

**Phase:** 3 (Data Quality & Experiment Validation)
**Notebook:** `notebooks/02_data_quality.ipynb`
**Dataset:** `cookie_cats.csv`, 90,189 rows x 5 columns, one row per player.
**Verdict:** **Valid for analysis, with limitations** (listed in section 4).

All rules below were written in the notebook **before** the checks were run. Retention by group was deliberately **not** computed in this phase.

---

## 1. Results

| Check | Result |
|---|---|
| Missing values (5 columns) | 0 in every column |
| Fully duplicated rows | 0 |
| Duplicated `userid` | 0 (90,189 unique ids in 90,189 rows) |
| Users appearing in both groups | 0 |
| Values of `version` | Only `gate_30` and `gate_40` |
| Retention columns | Boolean, only True / False |

## 2. `sum_gamerounds`: distribution and the extreme value

| Statistic | Value |
|---|---:|
| Mean | 51.87 |
| Median | 16 |
| 75th percentile | 51 |
| 95th percentile | 221 |
| 99th percentile | 493 |
| 99.9th percentile | 1,073.6 |
| Maximum | 49,854 |

The distribution is strongly right-skewed: the mean is more than three times the median.

**One record stands out.** The largest value (49,854 rounds, `userid` 6390605, group `gate_30`) is about 17 times the second largest (2,961). Over 14 days it averages 3,561 rounds per day, or about 148 per hour around the clock. We cannot tell from the data whether this is a tracking error, automated play, or a real player.

Why it matters for the analysis:
- Retention metrics are not affected in any meaningful way: it is one player out of about 44,700 in `gate_30`, and it contributes a single True/False.
- Mean `sum_gamerounds` **is** affected. This one player adds about 1.1 rounds to the `gate_30` mean (about 2% of a mean near 52), which is not negligible in a comparison of means.

## 3. Decisions

| Topic | Decision | Reason |
|---|---|---|
| Missing values | None to handle | Zero missing |
| Duplicates | None to handle | Zero duplicated rows or ids; no user in both groups |
| Invalid `version` | None to handle | Only the two expected values |
| Negative `sum_gamerounds` | None to handle | Zero found |
| Zero `sum_gamerounds` | **Keep** | Valid value (installed, did not play) |
| Extreme `sum_gamerounds` (91 flagged, incl. the 49,854 record) | **Keep, keep the flag column `is_extreme_rounds`** | The rule set before the checks was "flag, do not delete". Deleting after seeing the data would be a post-hoc choice. Effect is tested in Phase 6. |
| Zero rounds with `retention_1 = True` (87 players) | **Keep** | About 0.1% of rows, cannot be explained from the data. The source describes retention as "came back and play", so these rows conflict with that description (or rounds were not tracked). Tested in Phase 6. |
| SRM | **Pass** (not flagged) | p = 0.0086 is above the threshold fixed beforehand (0.001). The threshold is not changed after seeing the result. |

No rows are removed. `data/processed/validated_cookie_cats.csv` is therefore expected to have **90,189 rows and 6 columns** (the 5 original columns plus `is_extreme_rounds`). It stays local and is listed in `.gitignore`.

## 4. Limitations and notes

- **SRM is borderline-visible, not failed.** The split is 49.56% / 50.44%. The p-value (0.0086) is below the usual 0.05 but above the threshold set in advance for this check. It is reported openly instead of being hidden, and any imbalance is treated as an open question when interpreting the result.
- **No baseline balance check is possible.** The dataset has no pre-experiment player attributes, so only group sizes can be checked.
- **No timestamps or player attributes.** Time trends, novelty effects and segments cannot be analysed.
- **`retention_7` definition is unclear** in the source ("exactly day 7" vs "within 7 days"). The data does not resolve it.
- **Windows differ:** `sum_gamerounds` covers 14 days; retention flags refer to day 1 and day 7.
- **Revenue is not in the data.** Conclusions are about retention and activity only.
